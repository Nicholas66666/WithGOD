# Presence 核心交互待讨论清单

更新日期：2026-05-29

这份文档记录当前还需要策略确认的交互边界。原则是：不增加用户心智负担，不破坏「按一下，说话；再按一下，结束」。

## 已确认交互

### Action Button

- 空闲时按：开始录音。
- 录音中按：停止录音。
- 处理中按：忽略，避免重复上传。
- App 前台、后台、未启动都应尽量保持同样行为。

### Watch 屏幕按钮

- 空闲时显示「开始记录」。
- 录音中显示「结束记录」。
- 停止时复用同一个 `stopRecording()`。

### 误触

- 3.5 秒以内录音直接丢弃。
- 不上传、不分析、不生成 iPhone 记录。

## 还没有完全考虑清楚的核心交互

### 1. 处理中是否允许取消？

当前策略：处理中按 Action Button 忽略。

待讨论：

- 用户如果录错了，但已经进入上传整理，是否需要「取消这条」？
- 如果允许取消，是只取消 UI 等待，还是也尝试删除服务端记录和音频？

建议策略：

- 第一阶段继续忽略，不增加复杂度。
- iPhone 列表负责删除。
- 后续如果用户强烈需要，再加「处理中长按取消」或 iPhone 删除远端记录。

### 2. Quick Response 显示后，Action Button 应该做什么？

当前推测：显示回应后再次按 Action Button 应该开始新录音，并清掉当前回应。

待验证：

- 用户看到回应后，按 Action Button 更可能是想开始下一条，而不是关闭卡片。

建议策略：

- Action Button 在回应态按下：开始新录音。
- 屏幕点卡片：关闭回应回到空闲。

### 3. 录音中打开 iPhone App 是否应有实时状态？

当前没有。

待讨论：

- iPhone 是否需要知道 Watch 正在录音？
- 如果 iPhone 打开时显示「Watch 正在记录」，可能有安全感，但也会增加同步复杂度。

建议策略：

- 暂不做。
- 优先保证 Watch 独立可靠。

### 4. 长录音是否需要中途提示？

当前只有 60 秒静音保护，没有长录音时长提示。

待讨论：

- 如果用户录 5 分钟、10 分钟，Watch 是否应该震动提醒仍在录？
- 提醒可能有帮助，也可能打断祷告。

建议策略：

- 不做强打断。
- 后续可考虑低频、轻触感、可关闭的“仍在记录”提示。

### 5. 自动静音停止后的反馈

当前静音保护会调用 `stopRecording()`，对用户来说可能和手动停止无区别。

风险：

- 用户可能不知道是系统因静音停止。
- 如果误判，会造成体验灾难。

建议策略：

- 下一阶段 Recording Stability 中加入 stop reason。
- 静音停止后 Watch 回应里明确标记「因长时间安静自动结束」。

### 6. 失败后如何重试？

当前失败提示是「记录已保存，但暂时无法生成反馈」。

待讨论：

- Watch 是否应该提供重试按钮？
- iPhone 是否作为主要重试入口？

建议策略：

- Watch 不增加复杂按钮。
- iPhone 详情页未来可提供重试/重新分析。

### 7. 删除是否只删本地？

当前 iPhone 删除主要删除本地记录和本地音频 artifact。

待讨论：

- 删除是否也要删除 Supabase 记录和 Storage 音频？

建议策略：

- 后续需要做远端删除，否则服务端同步可能重新拉回记录。
- 这属于 iPhone 数据管理，不影响 Watch 核心入口。

## 推荐优先级

1. 保持当前 Action Button toggle，并让用户真机测试。
2. 下一步补 recording diagnostics，记录 stop reason。
3. 再处理 Quick Response 显示后 Action Button 新录音策略。
4. 最后处理远端删除、重试、长录音提示等增强交互。
