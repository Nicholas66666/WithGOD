# Presence 核心交互原则

更新日期：2026-05-29

## 最核心原则

与神同在的核心价值是：在用户最需要记录、回转、祷告、求助或捕捉灵感的时候，用最低摩擦把话说出来，并可靠保存。

交互必须保持极简：

- 用户不需要先判断 App 状态。
- 用户不需要思考当前在前台、后台还是未启动。
- 用户不需要记复杂操作。
- Action Button 是最低摩擦入口。
- 屏幕按钮是可见的等价入口。
- 已经调通的启动体验不能被后续优化破坏。

## 录音状态机

当前 Watch 端只有三个主要状态：

```text
空闲
-> 正在录音
-> 正在上传整理
-> 空闲 / 显示回应
```

所有入口都应该围绕这个状态机工作，而不是各自实现一套流程。

## Action Button 逻辑

Action Button 通过快捷指令/AppIntent 触发同一个 Watch 请求。

期望行为：

- App 在前台，未录音：按 Action Button，开始录音。
- App 在后台，未录音：按 Action Button，唤起并开始录音。
- App 未启动，未录音：按 Action Button，冷启动并开始录音。
- App 在前台，正在录音：按 Action Button，停止录音。
- App 在后台，正在录音：按 Action Button，唤起并停止录音。
- 正在上传整理：按 Action Button 不应重复上传或打断当前整理。

停止录音时必须复用屏幕「结束记录」按钮的同一条 `stopRecording()` 流程。

这意味着：

- 3.5 秒以内误触录音直接丢弃。
- 超过 3.5 秒正常上传和分析。
- Watch 回应、iPhone 新记录、录音播放、转写/分类同步都走同一条链路。

## 屏幕按钮逻辑

Watch 屏幕按钮是 Action Button 的可见等价入口。

- 空闲时显示「开始记录」，点击后开始录音。
- 录音时显示「结束记录」，点击后停止录音。
- 正在上传整理时显示处理中状态，不应产生第二次上传。
- 显示回应后，用户可以完成/返回空闲。

## 去重原则

一次物理 Action Button 点击可能经由多个系统通道抵达 Watch App，例如 AppIntent 通知和 URL 打开事件。

因此 Watch 端必须对短时间内重复到达的同一触发做去重，避免：

- 一次点击先开始录音，又被重复事件立刻停止。
- 一次点击先停止录音，又被重复事件再次开始。
- 正在上传整理时产生重复处理。

当前去重窗口为 1 秒。

## 不应引入的复杂性

后续优化不能牺牲简单性：

- 不要让用户选择「开始」或「停止」两套快捷指令。
- 不要要求用户根据 App 状态选择不同按钮。
- 不要为了省电牺牲录音可靠性。
- 不要用高频轮询换体验。
- 不要让 Action Button 的行为和屏幕按钮产生不同结果。

## 后续优化方向

后续可以优化：

- 录音稳定性诊断。
- 低电量和后台状态下的明确提示。
- Deep Response 语音对话入口。
- Quick Response 的经文回应质量。

但所有优化都必须保留这一条主线：

```text
按一下，说话；再按一下，结束。
```

## Deep Response 的实时体验原则

Deep Response 是单独的高实时性体验。它的核心价值是流畅语音对话，而不是省电本身。

进入 Deep Response 后，允许为了首响、打断和连续对话自然度，让 Watch 承担必要的本地实时处理，例如：

- 本地 VAD。
- 音频预处理。
- 实时上传。
- 流式播放。
- 打断检测。

但这些能力不能反向污染普通 Quick Response 的极简入口。普通记录仍然保持：

```text
按一下，说话；再按一下，结束。
```
