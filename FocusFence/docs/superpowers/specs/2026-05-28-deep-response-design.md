# Deep Response 设计规格

日期：2026-05-28

相关技术 POC 规格：

- `2026-05-29-deep-response-xiaozhi-poc-spec.md`

## 目标

Deep Response 用于强情绪、创伤闪回、极深痛苦祷告、强烈忧虑、羞耻、恐惧等场景。

它不是把 Watch 上的一屏文字写长，也不是 3-5 步指导卡片。它要在用户需要时，开启一段以圣经为中心、可语音互动、低延迟、能真实承接痛苦的属灵陪伴对话。

## 产品定位

Deep Response 是「Scripture Companion」。

它做的是：

- 呼唤用户的名字。
- 具体命名用户正在经历的痛苦。
- 带用户进入一节可靠经文。
- 用经文帮助用户重新看见现实。
- 通过语音对话继续陪用户说下去。

它不是：

- AI 假装神说话。
- AI 假装圣灵直接启示。
- 心理治疗诊断。
- 长篇属灵教导。
- 一次性文字总结。

## 入口体验

Deep Response 不默认打开。它从 Quick Response 后进入。

当系统判断用户处在强情绪或强痛苦中时，Watch 先给一个短锚点，然后出现邀请：

- `要我陪你聊一会儿吗？`
- `要一起回到经文里吗？`
- `要我陪你停在这节经文里吗？`

用户确认后，才进入 Deep Response。

## 语音优先

Deep Response 必须以语音对话为核心体验。

原因：

- 强情绪时读小屏文字很困难。
- 一行经文可能太薄，无法承接复杂痛苦。
- 语音可以提供节奏、停顿、呼唤名字和被陪伴感。
- 对话可以根据用户继续说出的内容调整，而不是一次性输出固定流程。

技术上，Deep Response 需要真正的 realtime：

- Watch 麦克风持续流式上传。
- 服务端实时转写。
- 模型低延迟生成短句。
- 必要时流式语音播放。
- 用户可以继续说，系统能接着回应。

## 技术路线决策

Deep Response 的主力方案暂定为「小智式级联语音链路」，而不是当前已经跑通的 OpenAI Realtime JSON smoke test。

Deep Response 的第一优先级是语音沟通流畅性：

- 首响快。
- 可打断。
- 不明显卡顿。
- 连续对话自然。
- 强情绪里第一句能及时承接用户。

功耗是重要约束，但不是第一优先级。不能为了省电牺牲 Deep Response 的核心价值。

主链路目标：

```text
持续音频输入
-> 流式 ASR
-> 流式 LLM
-> 流式 TTS
-> 首句音频尽快播放
```

选择这个方向的原因：

- 用户已经实测小智式链路可以做到接近“说完立刻响起”的体验。
- Deep Response 的关键不是最终完整回答速度，而是第一句安慰性语音的首响速度。
- 级联链路可以分别观测 ASR 首字、LLM 首 token、TTS 首包和播放首帧，便于优化。
- ASR、LLM、TTS 可以独立替换，国内/海外部署时可按延迟和质量选择供应商。

## Watch / iPhone / Server 分工原则

Deep Response 阶段不能预设 Watch、iPhone、server 的固定分工。分工必须由 POC 数据决定。

允许 Watch 承担必要的实时任务：

- 本地 VAD / 端点检测。
- 音频预处理、降噪、增益或编码。
- 实时音频分片上传。
- 接收流式文本或音频。
- 播放流式 TTS。
- 用户打断检测和 cancel 信号。

不应让 Watch 承担的任务，除非 POC 证明值得：

- 本地 ASR。
- 本地 LLM。
- 本地 TTS。
- 长期复杂上下文管理。
- 非实时的完整整理和长期同步。

iPhone 不应被默认放进首响关键路径。只有当 POC 证明 iPhone relay 更快、更稳或能明显改善体验时，才让 iPhone 参与 realtime path。

server 适合承担：

- Streaming ASR / LLM / TTS 编排。
- 会话上下文。
- 存储。
- 非实时补全和完整整理。

最终判断标准不是“哪个设备更省电”，而是谁能让首响、打断和连续对话更流畅。

OpenAI Realtime 仍保留为对照 POC，但不是默认主线。

OpenAI Realtime 只有在满足以下条件时，才进入 Deep Response 主链路候选：

- 使用真正的 voice agent 方式，而不是当前的“音频流入、结束后生成完整 JSON”方式。
- 使用持续会话、音频增量输出和可打断机制。
- 首句音频播放时间稳定达到目标。
- 打断体验、语气自然度和连续对话稳定性明显优于级联链路。

历史 Watch Realtime smoke test 已被后续 HTTP-only 决策 superseded。它只证明：

- Watch 模拟器可以建立 WebSocket。
- Watch 可以把 PCM 分片发到 Supabase。
- Supabase 可以连 OpenAI Realtime 并返回一屏文本回应。

它没有证明，也不再作为 Deep Response 后续目标或候选路线：

- 真机 Watch 麦克风持续 realtime 采集稳定。
- 端到端语音首响足够快。
- 支持自然打断。
- 适合作为 Deep Response 的主语音对话链路。

2026-06-05 纠正：后续 Deep Response Watch 端完全不再考虑 WebSocket。Watch transport 固定采用 HTTP upload/download/polling/streaming 形态，开发验证采用自测试模式；用户人工 Watch 测试不作为阶段计划或验收门槛。

## 延迟验收指标

Deep Response 的技术选型以可感知体验为准，不以供应商或接口名称为准。

核心指标：

- 用户停止说话到第一段语音开始播放：目标小于 1.5 秒，最多不超过 2 秒。
- 用户打断系统说话到系统停止旧音频：目标小于 500 毫秒。
- 连续 5-10 分钟对话不出现明显延迟漂移、断流或上下文错乱。
- 强情绪场景下，第一句必须足够短、具体、安慰，而不是等待完整长回答。
- POC 必须分别记录 Watch 本地处理、网络、ASR 首字、LLM 首 token、TTS 首包、播放首帧耗时。

如果 OpenAI Realtime 在真实 POC 中不能稳定达到这些指标，则不作为 Deep Response 主链路。

## 身份边界

Deep Response 的身份必须被严格约束。

允许说：

- `Mike，我听见你现在真的很辛苦。`
- `我们先不要急着解释这一切。`
- `圣经说，耶和华靠近伤心的人。`
- `这不是要你立刻变坚强，而是提醒你：你现在不是独自承受。`
- `你愿意告诉我，刚才最刺痛你的是什么吗？`

禁止说：

- `我是神，我对你说。`
- `圣灵现在告诉你。`
- `神一定要你这样做。`
- `这件事发生是因为神要教你。`
- `你只要有信心就不会痛苦。`
- `我医治你。`

推荐身份定义：

> 一个以圣经为中心的属灵陪伴者，帮助用户和圣经对话；不代替神，不代替圣灵，不替用户解释神的隐藏旨意。

## 名字使用规则

Deep Response 可以使用用户名字，因为强情绪中被具体呼唤会显著增强安慰感。

规则：

- 名字必须来自用户设置，不能由模型猜测。
- 只在对话开始或关键安顿句中使用。
- 不要每句话都叫名字。
- 语气必须真实、克制、温柔。

示例：

> Mike，我听见你现在真的很累。我们先不要急着把自己讲明白。圣经说，耶和华靠近伤心的人。此刻我们先停在这里：祂不是远远看着你崩溃，祂靠近破碎的人。

## 对话方式

Deep Response 不输出完整讲章。它以短句推进：

1. 命名痛苦。
2. 引入经文。
3. 把经文和当下痛苦连接起来。
4. 问一个小问题。
5. 根据用户回答继续陪伴。

每轮回应应短，适合 Watch 和耳机：

- 1-3 句话。
- 一次只问一个问题。
- 少解释，多陪伴。
- 不急着解决。

## 强情绪触发条件

优先触发 Deep Response 邀请：

- 用户表达崩溃、害怕、强烈难过、创伤闪回。
- 用户说自己撑不住、很痛、很孤独、很羞耻。
- 用户祷告里出现明显哭诉、求救、绝望、被过去拉住。
- 用户反复说同一类强痛苦，说明一句回应不够。

不触发：

- 普通灵感。
- 待办。
- 普通日记。
- 普通问题。
- 轻微情绪记录。

## 安全边界

如果用户表达自伤、伤人、立即危险或极端绝望：

- 不只做属灵安慰。
- 要温柔建议联系现实中的可信任人、牧者、家人或当地紧急支持。
- 不承诺保密到危及安全。
- 不把危机简化为属灵问题。

## 与 Quick Response 的关系

Quick Response 是锚点。

Deep Response 是进入对话。

流程：

```text
录音结束
-> Quick Response 给一屏锚点
-> 如果检测到强情绪，显示 Deep Response 邀请
-> 用户确认
-> 开启 Scripture Companion 语音对话
```

## 验收标准

1. 强痛苦场景不会只给一句薄回应。
2. Watch 不展示长篇指导文字。
3. 用户能明确选择是否进入对话。
4. 对话会呼唤用户名字，但不过度使用。
5. 对话基于圣经，不冒充神或圣灵。
6. 每轮回应短、慢、具体、可继续。
7. 危机表达进入安全回应边界。
8. 技术实现必须基于稳定 realtime，不能靠长轮询或高耗电方案硬撑。
